# 语言支持

[English](languages.md) · **简体中文**

为了更好地做代码分析，Clew 会针对不同语言的特性，提供贴合它的支持。目前 Clew 提供的功能完整支持 Rust、Python、TypeScript/JavaScript、Go、Dart、Java、C#、PHP、Ruby、Erlang、Haskell 和 Zig；C 和 C++、Lean 4 以及 SQL 支持其中的大部分功能；对其余语言目前也提供了一些基础支持，如语法高亮。未来会支持更多语言。

**设置 → 语言服务器** 会针对当前打开的项目，显示每种语言的语言服务器及其状态，并让你为每种语言做设置——每项设置都先显示当前生效的内容，再列出可选项：

- **Python** —— 语言服务器和调试器所使用的解释器，以及由谁指定（你的选择、项目的 `.clew/lsp.toml`、为项目找到的环境）。可以从 Clew 找到的环境中另选一个（项目自身的、Poetry、Pipenv、Hatch、PDM、conda、pyenv、uv，或 `PATH` 上的 `python3`），也可以直接填写路径。语言服务器默认是 pyright，也可以在 **任意语言** 中另选：basedpyright、pylsp、jedi-language-server、ruff、ty 和 pyrefly 都会以各自提供服务的方式运行，并在各自读取的位置得到解释器和环境中的包。
- **Rust** —— rust-analyzer 加载项目时启用的 Cargo features（从各 package 的 `Cargo.toml` 中列出全部 features；也可以全部启用，可选是否带默认 features），以及检查所针对的 target。
- **Go** —— gopls 和调试器构建时使用的 build tags（列出项目中 `//go:build` 行用到的 tags），以及按哪个 `GOOS`/`GOARCH` 阅读项目。
- **C 和 C++** —— clangd 使用的 `compile_commands.json`（列出 CMake、Meson 等在项目中生成的那些），以及编译数据库未覆盖的文件所用的编译参数（如 `-DDEBUG -Iinclude -std=c++20`）。
- **Lean 和 Dart** —— 语言服务器所用的工具链：elan 安装的各个工具链（项目 `lean-toolchain` 指定的排在最前）、Flutter SDK 以及 fvm 管理的各个版本（项目指定的排在最前）。
- **TypeScript 和 JavaScript** —— 语言服务器所运行的 TypeScript：默认使用 Clew 自带的版本，除非你主动选择，否则绝不会使用项目自带的版本（列表中会标出它的版本，并注明它会运行项目自身的代码），也可以选择全局安装的版本。
- **Zig** —— zls 所使用的 `zig` 编译器：zvm 和 zigup 管理的各个版本（项目 `build.zig.zon` 要求的版本排在最前），或你指定的编译器。
- **Java** —— Eclipse JDT 语言服务器构建项目所用的 JDK：本机上的各个 JDK（`JAVA_HOME`、`/usr/lib/jvm`、macOS、SDKMAN!、IntelliJ、asdf、mise 和 Homebrew 安装的），构建要求的 Java 版本（`.java-version`、`.sdkmanrc`、Gradle 工具链、`pom.xml`）对应的排在最前。
- **PHP** —— intelephense 按哪个 PHP 版本解读代码（`composer.json` 允许的最低版本排在最前）。
- **C#** —— csharp-ls 打开的解决方案：项目根目录及下一级目录中的 `.sln` 和 `.slnx` 文件。
- **Kotlin、Scala 和 Elixir** —— 要运行的语言服务器：JetBrains 的 Kotlin LSP（或社区的 kotlin-language-server）、Metals（在 Coursier 安装的位置查找）、Expert（或 ElixirLS）；否则用你 `PATH` 上的。
- **Ruby、Erlang 和 Haskell** —— 选用哪个 Ruby 的 Ruby LSP（rbenv、chruby、asdf、mise、RVM 安装的；项目 `.ruby-version` 指定的排在最前），以及要运行的 ELP 和 Haskell 语言服务器（ghcup、Stack、Cabal 安装的），或 `PATH` 上的。
- **任意语言** —— 使用你自己的语言服务器程序：另一个版本的 Clew 自带服务器、另一种服务器，或为 Clew 尚无服务器的语言指定一个。会构建项目的服务器在构建前仍会先征得你的同意。打开 **与该语言的服务器同时运行** 后，这个程序会作为第二个服务器与该语言自己的服务器一起运行（例如在 pyright 旁边运行 ruff）：它会收到同样的文件，它的警告与第一个服务器的警告一起显示——加下划线、计入状态栏、悬停时说明——而跳转到定义、查找引用和悬停文档仍由第一个服务器提供。

以上内容都只通过读取文件得到——不会运行任何程序；远程项目则在其所在主机上查找。这些选择保存在 Clew 自己的数据目录中，只对本机上的这个项目生效，绝不会写入项目，优先于项目的 `lsp.toml`，并同样作用于编辑器的语言服务器、调试器以及 Ask 的代码工具。

某种语言的服务器还没有安装时，Clew 会先问你，再下载它自己的那一份。如果这个服务器程序已经在你的 `PATH` 上——rustup 装的 rust-analyzer、你自己装的 clangd——提问里也会给出它；能回答版本号的会先问它的版本，这样版本管理器为一个并未安装的工具留下的垫片（shim）就不会被提供（TypeScript 的从不提供：Clew 自带的服务器固定了它所运行的 TypeScript，而你自己的服务器会从项目里取 TypeScript）。点击 **使用已有的**，它就成为这门语言的服务器，和在这里选中它一样，什么都不会下载。你自己装的 pyright 或 basedpyright 会直接使用：不提问、不下载，也不需要 Node；只有项目固定了 pyright 的版本时才会安装那个版本。

构建因此不会编译的代码会在阅读时变暗：Rust 中依赖未启用 feature（或其他平台）的 `cfg` 项、`//go:build` 行或 `_windows.go` 这类文件名所排除的 Go 文件，按平台和 `-D`/`-U` 参数会被预处理器丢弃的 C/C++ `#if`/`#ifdef` 分支，Zig 中基于 `builtin.os.tag` 或 `builtin.cpu.arch` 的 comptime `if`/`switch` 分支里编译器不会为该平台分析的部分，C# 中依据文件自身 `#define` 的符号判定不成立的 `#if` 分支，Haskell 中（启用了 CPP 的文件）基于 `<os>_HOST_OS` 和 `<arch>_HOST_ARCH` 的 CPP `#if` 分支，以及 Erlang 中依据文件自身 `-define` 的宏判定不成立的 `-ifdef`/`-if` 分支。与平台有关的判断，以状态栏中选定的平台为准。只有确定不会编译的代码才会变暗——可能由其他 package 启用的 feature、可能由头文件定义的宏，都不会被处理。

- **SQL**：大纲列出 schema 中的表（及其列）、视图、函数、触发器和类型，并以其上方的 `--` 注释作为文档；类型图会按外键把表连接起来（无论外键写在表定义中，还是像 `pg_dump` 那样写在同一文件的 `ALTER TABLE` 里），并把每个视图连向它所查询的表。没有语言服务器时，由项目的数据库结构在代码中作答：指针（Alt）或光标处（显示信息）下的表或列会显示结构对它的描述 —— 表的列、键、索引、策略和触发器；列的类型、默认值、注释和引用 —— 转到定义会跳到创建它的语句。名称按书写方式解析（`schema.table`、`alias.column`），适用于 SQL 文件、Prisma schema 以及其他代码中的 SQL 行。薄弱点会列出没有主键的表、没有索引的外键、在同一 schema 其他表已启用时仍关闭的行级安全，以及删除数据、添加无默认值的 `NOT NULL` 列或阻塞表写入（未使用 `CONCURRENTLY` 建索引、修改列类型）的迁移。
- **光标处的测试，覆盖所有编译型语言和 BEAM 语言**：Go 的 `func TestX`（以及基准测试、模糊测试和示例）、Java、Kotlin 和 Scala 里 JUnit 的 `@Test` 方法、ScalaTest 和 MUnit 的 `test("…")`、xUnit 的 `[Fact]` 和 `[Theory]`、NUnit 的 `[Test]` 和 MSTest 的 `[TestMethod]`、Dart 的 `test` 和 `group`（以及 Flutter 的 `testWidgets`）、RSpec 的 `it` 和 `describe`、Minitest 的 `test_x`、Zig 的 `test` 块、EUnit 的 `_test` 函数和 Common Test 套件里的用例、ExUnit 的 `test` 和 `describe`、hspec 和 Tasty 的测试、GoogleTest 的 `TEST` 和 Catch2 的 `TEST_CASE` 都会在行号旁标出；**Run Test** 用项目自己的命令、在项目所在的地方运行光标处的测试（或它所在的组，或整个文件）：在模块里执行 `go test -run`，JUnit 用 Gradle（优先用它的 `gradlew`）或 Maven（`mvnw`），Scala 用 sbt、Mill 或 scala-cli，`dotnet test --filter` 按测试的全名，`dart test` 或 `flutter test` 按名字，`rspec file:line`（有 Gemfile 时经由 Bundler），Rails 的 `rails test file:line` 或 Minitest 的 `-n`，`zig test --test-filter`，rebar3 的 `eunit --test` 或 `ct --case`，`mix test file:line`，Cabal 或 Stack 配合 hspec 的 `--match`（Tasty 用 `--pattern`），以及在 CMake 构建目录里执行 `ctest -R`。**调试测试**在该语言的调试器下运行同一条命令，并在你的断点处暂停：Go 用 Delve 的测试模式，Ruby 在 rdbg 下运行（RSpec、Rails 和 Minitest 均可），Dart 和 Flutter 用各自的测试适配器，JUnit 通过 Gradle、Maven 或 sbt 运行、测试 JVM 置于 Clew 的 Java 调试器之下（它按源文件找到 Kotlin 或 Scala 文件编译出的类，例如 `Cart.kt` 的 `CartKt`），CTest 的测试以其自己的程序和参数（即 `ctest --show-only` 列出的）在 lldb 下运行，Zig 的测试则单独为它构建。即使调试器不报告退出码（Delve 和 rdbg 就不报告），运行结束时也会给出测试结果——从测试运行器的最后一行读出。EUnit 和 ExUnit 的测试在 OTP 解释器（Clew 的 Erlang 调试器）下运行：EUnit 用它自己对该测试的调用（文件以 `TEST` 宏编译），ExUnit 按 `mix test file:line` 的方式运行，并先编译测试文件，因此测试本身中的断点和它所调用代码中的断点都会命中。C# 的测试按 `dotnet test` 的方式运行，其测试宿主等待 netcoredbg 附加（VSTest 的宿主调试）：测试本身及其调用的代码中的断点都会命中，运行以 VSTest 的汇总和其退出码结束。Haskell 的测试在测试套件的 REPL（`cabal repl test:spec`、`stack ghci`）中，由 GHCi 的调试器运行套件的 `main`，并按 hspec 的 `--match`（Tasty 的 `--pattern`）选出该测试：测试失败时，运行以其退出码结束，而不是停在测试运行器自己的退出处。构建把测试放在调试器够不到的地方运行的（Mill、scala-cli、设置了 `fork := true` 的 sbt 构建），会在没有调试器的情况下运行，并说明这一点。
- **Kotlin、Scala 和 Elixir**：语法高亮；大纲（Kotlin 的类、接口、枚举及其条目、object 和 companion、函数、类或文件级的属性、类型别名；Scala 2 和 3 的包、trait、枚举和 case、类、object、函数、val 和 var、given 以及类型；Elixir 的模块、函数 —— 同一个函数的多个子句算作一项，同名但元数不同的算作另一项 —— 宏和 `@type`），每个定义带上它的文档（KDoc、Scaladoc —— 其中的 `{{{ }}}` 代码和 `[[链接]]` 转成 Markdown —— 以及 Elixir 的 `@doc`，heredoc 或字符串都行，会越过它下面的 `@spec`）；公开 API 按各语言的规则判断（Kotlin 的 `private`、`protected` 和 `internal`，Scala 的 `private` 和 `protected`，Elixir 的 `defp`）；import 按构建的方式解析 —— Kotlin 和 Scala 通过 Java 的解析器，三者之间可以互相解析（`src/main/kotlin`、`src/main/scala` 或 `src/main/java` 下的类，`*` 对应它的包，Kotlin 的顶层函数对应它的包），Elixir 的 `alias`、`import`、`use` 和 `require` 按 Mix 的文件约定（`Shop.Pricing.Tax` 对应 `lib/shop/pricing/tax.ex`，umbrella 应用里的也一样）；调用图（Java、Kotlin 和 Scala 之间可以互相调用）；Weak Spots；以及语言服务器（见上文）。**Run** 按项目运行程序的方式运行：Kotlin 脚本用 `kotlinc -script`，Kotlin 程序用它的 Gradle 构建的 `run`，Scala 用 sbt 的 `run` 或 scala-cli，Elixir 在 Mix 项目里用 `mix run`（脚本会在加载项目后运行），否则用 `elixir`；**Debug** 在该语言的调试器下运行同一个程序：Kotlin 和 Scala 的 JVM 由 Clew 的 Java 调试器调试（由 Clew 的 init 脚本把调试代理加到 Gradle 的 `run` 上，通过 `JAVA_OPTS` 加到 `kotlinc` 的 JVM 上，或加到 sbt 自身的 JVM、scala-cli 的 JVM 上），断点按源文件定位；Elixir 在 OTP 解释器下运行：解释 Mix 项目自己的模块，启动其应用（有监督树时保持运行）或加载脚本，变量以 Elixir 中的名字显示，宏所在的行（如 `assert`）只停一次。fork 出 `run` 的 sbt 构建以及远程项目的程序会在没有调试器的情况下运行，并说明这一点。Weak Spots 会找出 Kotlin 的 `!!` 和 `TODO()`、Scala 的 `???`、`Option.get` 和 `asInstanceOf`、Elixir 的 `Code.eval_string`、`String.to_atom` 和 shell 调用，以及其他编译型语言各自的问题：C# 的空值容忍运算符 `!.`、`Process.Start` 和 `BinaryFormatter`，Dart 的 `!.` 和 `Process.run`，Haskell 的 `fromJust`、`undefined` 和 `unsafePerformIO`，Zig 的 `.?`、`catch unreachable` 和指针转换，Erlang 的 `os:cmd`、`binary_to_term` 和 `list_to_atom`，Go 的 `unsafe.Pointer` 和 `log.Fatal`，Java 的 `ObjectInputStream` 和 `ProcessBuilder`，Ruby 的 `instance_eval`、`YAML.load` 和 `html_safe` —— 只看代码，不看字符串和注释，也不看测试（包括 `.Tests` 项目和 Common Test 套件）。
- **Java、C#、PHP、Ruby、Erlang、Haskell 和 Zig**：语法高亮；大纲，每个定义附带其文档（Javadoc、C# 的 `///` XML 文档、PHPDoc、Ruby 的 `#` 注释、EDoc、Haddock、Zig 的 `///`），并标出测试（JUnit、NUnit/xUnit/MSTest、PHPUnit、Minitest、EUnit、Zig 的 `test` 块）；导入图；调用图；以及语言服务器（Eclipse JDT LS、csharp-ls、intelephense、Ruby LSP、ELP、Haskell 语言服务器、zls）。调试器用 rdbg（`debug` gem；所选 Ruby 自带的那个）运行 Ruby 程序，用 netcoredbg 运行 .NET 程序集，把 Zig 程序当作原生代码交给 lldb-dap（`.zig` 文件会在本次调试中经 LLVM 编译，即 `-fllvm`，lldb 能读取其调试信息；由 Zig 自带代码生成器——x86-64 上 Debug 构建的默认方式——生成的二进制同样可以调试，但 lldb 无法从中读取变量，调试控制台会说明这一点以及如何构建出它能读取的版本）；并通过 Clew 自带的调试适配器，经 JDWP 调试 Java 程序（只需项目选定的 JDK：`.java` 文件会在本次调试中编译；构建出的程序以 `mainClass` 和 `classPaths` 指定；断点在其类加载时设置；可读取局部变量、字段、数组与字符串；JDWP 本身不求值，Clew 便在其上自行计算 Java 表达式——名字、字段、元素、字面量、算术、比较与逻辑运算、字符串拼接，以及 `order.total()`、`Math.max(a, b)`、`items.get(0) * 2` 这样的调用，按 Java 的规则选择重载并装箱或拆箱，方法只在已停下的线程中运行，途中遇到的断点会被跳过；悬停时不调用任何方法，暂停时也不调用，因为此时虚拟机不运行方法），用 Xdebug 3 调试 PHP 程序、用 OTP 的解释器调试 Erlang 程序（模块的 `main/1`，或启动配置指定的入口；其应用会在本次调试中以 `debug_info` 编译）、用 GHCi 的调试器调试 Haskell 程序（源码目录取自项目的 `.cabal` 或 `package.yaml`；启动配置也可改用 `cabal repl` 或 `stack repl`）。断点、单步、调用栈、变量和求值在这些语言中都可使用，以各语言自身调试器的能力为限：Erlang 和 Java 可以暂停正在运行的程序；PHP 在 Linux 上使用 Xdebug 3.4 及以上版本时（通过 Xdebug 的控制套接字），或在程序运行时仍接受命令的 Xdebug 下，也可以；GHCi 通过逐步执行直到函数返回来实现单步跳出，但无法暂停程序。没有启动配置时，C# 程序按 `dotnet run --project` 的方式运行，调试时先构建其项目（`dotnet build`），再在 netcoredbg 下运行其程序集；带 `main` 的 Zig 文件用 `zig run` 运行，调试时为本次会话单独构建，`build.zig` 项目的程序则用 `zig build run` 运行；库、测试项目或只有测试的 Zig 文件会说明它没有可运行的程序，并指向“运行测试”。以上全部在远程主机上同样可用：在该主机端口上监听的调试适配器（rdbg、Go 的 delve）由 Clew 的服务端通过自己的连接转发；Node.js 程序则由服务端自带的适配器经 Node 的 inspector 调试——Clew 在本机使用的 vscode-js-debug 会为每个被调试进程单独建立连接，远程通道无法承载。它支持带条件的断点、单步、真正的暂停（停在程序自己的代码中，而非 Node 内部）、已捕获与未捕获的异常、各作用域的变量，以及由 V8 自身完成的求值（悬停时不允许任何副作用）；TypeScript 按 Node 22.6 及以上版本的方式运行，类型在原位被剥除，因此每一行都与源码对应；它跟随主线程，不跟随 worker 或子进程。远程项目的 `composer.json` 和 Haskell 包描述文件在其所在主机上读取，因此其导入的解析与本地项目一致。导入按各语言的构建方式解析：Java 的包在项目的源码根目录（`src/main/java`）下查找，C# 的 `using` 指向项目文件所声明的命名空间，PHP 的类按 `composer.json` 的 PSR-4 映射及其 `require` 路径解析，Ruby 的 `require_relative` 以及从 `lib/` 解析的 `require`，Erlang 的 `-include`/`-include_lib` 与 `-behaviour`，Haskell 的模块在 `.cabal` 或 `package.yaml` 的源码目录下查找，Zig 的 `@import` 按路径解析；不属于项目的（JDK、NuGet、Composer 包、gem、OTP、Hackage、`std`）按包列出。
