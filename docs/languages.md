# Language support

**English** · [简体中文](languages.zh-CN.md)

To analyze code well, Clew tailors its support to each language's characteristics. Its features fully support Rust, Python, TypeScript/JavaScript, Go, Dart, Java, Kotlin, Scala, C, C++, C#, PHP, Ruby, Erlang, Elixir, Haskell and Zig; Lean 4 and SQL get most of them, and other languages get some basic support for now, such as syntax highlighting. More languages are coming.

**Settings → Language servers** shows, for the open project, each language's server and how it stands, and lets you set each language up — every setting shows what is in effect before what you can pick:

- **Python** — the interpreter the language server and debugger use, and who named it (your choice, the project's `.clew/lsp.toml`, an environment found for the project). Pick another from the environments Clew finds (the project's own, Poetry, Pipenv, Hatch, PDM, conda, pyenv, uv, or a `python3` on your `PATH`), or give a path. The server is pyright unless you name another under **Any language**: basedpyright, pylsp, jedi-language-server, ruff, ty and pyrefly each run the way they serve, and get the interpreter and the environment's packages where each reads them.
- **Rust** — the Cargo features rust-analyzer loads the project with (every package's features are listed from its `Cargo.toml`; or all of them, with or without the defaults), and the target it checks for.
- **Go** — the build tags gopls and the debugger build with (the tags the project's `//go:build` lines use are listed), and the `GOOS`/`GOARCH` to read the project for.
- **C and C++** — the `compile_commands.json` clangd uses (the ones CMake, Meson and others leave in the project are listed), and flags for files no compilation database covers (`-DDEBUG -Iinclude -std=c++20`).
- **Lean and Dart** — the toolchain their server runs from: elan's toolchains (the one the project's `lean-toolchain` names first), Flutter SDKs and fvm's versions (the project's first).
- **TypeScript and JavaScript** — the TypeScript the server runs: Clew's own by default, never the project's unless you choose it (it is listed, with its version, as running the project's code), or a global install.
- **Zig** — the `zig` compiler zls works with: zvm's and zigup's versions (the one the project's `build.zig.zon` asks for first), or one you name. zls is the release made for that Zig — zls works with the one Zig release it was built for — so a project on Zig 0.15 gets zls 0.15.1, one on 0.17 zls 0.17.0 (each from 0.13 to 0.17 downloaded and checked against its digest), unless the project's `lsp.toml` names a version.
- **Java** — the JDK the Eclipse JDT language server builds the project with: the JDKs on your machine (`JAVA_HOME`, `/usr/lib/jvm`, macOS's, SDKMAN!'s, IntelliJ's, asdf's, mise's and Homebrew's), the one of the Java version the build asks for (`.java-version`, `.sdkmanrc`, a Gradle toolchain, the `pom.xml`) first.
- **PHP** — the PHP version intelephense reads the code as (the lowest one `composer.json` allows first).
- **C#** — the solution csharp-ls opens: the `.sln` and `.slnx` files at the project's root and a folder down.
- **Kotlin, Scala and Elixir** — the server to run: JetBrains' Kotlin LSP (or the community kotlin-language-server), Metals (where Coursier installs it), Expert (or ElixirLS); the ones on your `PATH` otherwise.
- **Ruby, Erlang and Haskell** — the Ruby LSP of one of your Rubies (rbenv's, chruby's, asdf's, mise's, RVM's; the project's `.ruby-version` first), and the ELP and Haskell language server (ghcup's, Stack's, Cabal's) to run, or the ones on your `PATH`.
- **Any language** — a server program of your own: another build of Clew's server, another server, or one for a language Clew has none for. A server that builds the project still asks before it does. With **Run beside the language's server** on, the program runs as a second server next to the language's own (ruff beside pyright, say): it is sent the same files, and its warnings show with the first server's — underlined, counted in the status bar and said on hover — while definitions, references and hover docs stay the first server's.

Everything is found by reading files — nothing is run — and, for a remote project, on its host. The choices are kept in Clew's own data for this project on this machine, never written into the project, win over its `lsp.toml`, and reach the editor's language servers, the debugger and Ask's code tools alike.

A language whose server is not installed yet asks before Clew downloads its own copy. When the server's program is already on your `PATH` — rustup's rust-analyzer, a clangd you installed — the question offers it too — asked its version first where it answers it, so that a version manager's shim for a tool that is not installed is not offered (TypeScript's is never offered: Clew's own pins the TypeScript it runs, which a server of your own would take from the project): **Use that one** makes it the language's server, as choosing it here would, and nothing is downloaded. A pyright or basedpyright you installed is simply used, with nothing asked or downloaded and no Node needed, unless the project pins pyright's version.

The code the build then leaves out is dimmed as you read: Rust items behind a `cfg` of a feature the package builds without (or of another platform), Go files whose `//go:build` line or `_windows.go`-style name excludes them, C/C++ `#if`/`#ifdef` groups the preprocessor drops for the platform and the `-D`/`-U` flags, Zig's comptime `if`/`switch` branches on `builtin.os.tag` or `builtin.cpu.arch` the compiler does not analyze for the platform, C#'s `#if` groups of the symbols the file `#define`s, Haskell's CPP `#if` groups on `<os>_HOST_OS` and `<arch>_HOST_ARCH` (in a file that turns CPP on), and Erlang's `-ifdef`/`-if` groups of the macros the file `-define`s. Where it depends on the platform, the platform read for is the one picked in the status bar. Only what is certain is dimmed — a feature another package may turn on, or a macro a header may define, is left alone.

- **SQL**: the outline lists a schema's tables (with their columns), views, functions, triggers and types, each with the `--` comment above it as its doc, and the type graph draws the tables joined by their foreign keys — declared in the table or in an `ALTER TABLE` of the same file, as `pg_dump` writes them — and each view to what it selects from. With no language server, the project's schema answers in the code: a table or a column under the pointer (Alt) or at the caret (Show Info) peeks with what the schema says of it — a table's columns, keys, indexes, policies and triggers; a column's type, default, comment and what it references — and Go to Definition goes to the statement that makes it. Names are read as written (`schema.table`, `alias.column`), in SQL files, Prisma schemas and lines of SQL in other code. Weak Spots lists tables with no primary key, foreign keys no index leads with, row-level security left off where the schema's other tables have it, and migrations that drop data, add a `NOT NULL` column with no default, or hold writes to a table (an index built without `CONCURRENTLY`, a column's type changed).
- **Tests at the cursor, in every compiled language and on the BEAM**: Go's `func TestX` (benchmarks, fuzz targets and examples too), JUnit's `@Test` methods in Java, Kotlin and Scala, ScalaTest's and MUnit's `test("…")`, xUnit's `[Fact]` and `[Theory]`, NUnit's `[Test]` and MSTest's `[TestMethod]`, Dart's `test` and `group` (and Flutter's `testWidgets`), RSpec's `it` and `describe`, Minitest's `test_x`, Zig's `test` blocks, EUnit's `_test` functions and a Common Test suite's cases, ExUnit's `test` and `describe`, hspec's and Tasty's tests, GoogleTest's `TEST` and Catch2's `TEST_CASE` are marked in the margin, and so is a program's start — Go's `func main` of `package main`, C's and C++'s `main`, Java's `static void main`, Kotlin's `fun main` (top level, or an object's `@JvmStatic`), Scala's `def main`, `@main` or `object … extends App`, C#'s `Main` or a program's top-level statements, Dart's and Zig's `main`, Haskell's `main` of its `Main` module, an Erlang module's exported `main/1` and Ruby's `if __FILE__ == $0` — whose ▶ runs or debugs that file's program as Run and Debug do with no launch file, whatever a launch file names (a Go program's run ends with the exit code Delve reports; a Flutter app's runs under Flutter's own debug adapter, on this computer's desktop where the app has that platform, else in the browser where it has the web, else on the first device Flutter lists); **Run Test** runs the one at the cursor (or its group, or the file's) with the project's own command, where the project is: `go test -run` in its module, Gradle (its `gradlew` first) or Maven (`mvnw`) for JUnit, sbt, Mill or scala-cli for Scala (one MUnit test by its full name, a ScalaTest one by `-z`, a suite by its class, a file by its suites, a Mill program by its module's `runMain`), `dotnet test --filter` by the test's full name, `dart test` or `flutter test` by name, `rspec file:line` (through Bundler where there is a Gemfile), Rails' `rails test file:line` or Minitest's `-n`, `zig test --test-filter`, rebar3's `eunit --test` or `ct --case`, `mix test file:line`, Cabal or Stack with hspec's `--match` (Tasty's `--pattern`), and `ctest -R` from the CMake build. **Debug Test** runs the same command under the language's debugger and stops at your breakpoints: Go's by Delve's test mode, Ruby's under rdbg (RSpec, Rails and Minitest alike), Dart's and Flutter's by their test adapters, JUnit, MUnit and ScalaTest through Gradle, Maven, sbt, Mill or scala-cli with the test JVM under Clew's Java debugger (sbt's forked for it, the agent on it alone; scala-cli's given it with `--java-opt`; Mill's tests run in Mill's own JVM, by `testLocal`, which starts with the agent added to the project's `.mill-jvm-opts`) (which finds a Kotlin or Scala file's classes by their source file, `CartKt` for `Cart.kt`, and a stopped frame's file in whichever module it is, `core/src/main/scala` or Mill's `foo/src`), a CTest test's own program and arguments (as `ctest --show-only` lists them) under lldb, and a Zig test built for it — alone, or by its project's `build.zig` as a Zig program is (below), the test binary kept to that test. The run ends with the tests' verdict even where the debugger says no exit code (Delve's and rdbg's are read off the runner's last line). A runner's colours (sbt's, MUnit's diffs) show as colours in the run's output, not as escape codes. EUnit's and ExUnit's tests run under OTP's interpreter, Clew's Erlang debugger: EUnit's by its own call for the test (the file compiled with `TEST`), ExUnit's as `mix test file:line` runs them, the test file compiled first, so a breakpoint in the test itself is hit as well as one in the code it calls; a test held at a breakpoint is not timed out while you read it, EUnit's five seconds and ExUnit's minute lifted for the run (a test's own timeout still holds). A test that is a block a runner's call opens rather than a function — ExUnit's `test` and `describe`, RSpec's `it` and `describe`, Zig's `test`, MUnit's and ScalaTest's `test(…)`, Kotest's, GoogleTest's `TEST` (named `Suite.Name`), Catch2's `TEST_CASE`, Dart's `test` and `group`, hspec's `it` — is in the outline, and in the call graph as the caller of what it calls, so a function only tests call is called, not listed as possibly dead; and an Elixir module's function is reached as `Cart.add(…)`, an Erlang module's as `cart:add(…)`, from any module, with no import (an alias's last name too), as a class's is by its name from beside it with none — Java's, Kotlin's and Scala's in the same package, C#'s in the same namespace, Ruby's once required — and a C or C++ function or method by the header that declares it, wherever it is defined (`c.add(…)` in `main.cpp` reaches `int Cart::add` in `cart.cpp` through `cart.hpp`, included directly or by another header), never another file's `static` one. A call goes where the language sends it: a Go, Java, Kotlin or Scala file calls its package's other files with no import (Go's in its folder, the JVM languages' wherever they are filed, a Kotlin or Scala package's files found by the `package` they declare, and a Scala file's chained package clauses — `package cats.effect` then `package example` — opening the outer package's too), a C# file its namespace's and the enclosing namespaces' (a file saved with a byte-order mark, as Visual Studio saves them, in its namespace too); a value's declared type — a parameter's, a field's (`private final OwnerRepository owners;`, a Kotlin constructor's `val`), a local's — or `this` takes a method call to that type's method, the one it inherits from its nearest base (Go's from an embedded type, Ruby's from a module it includes) or a subtype's override, so `owners.findById(id)` on an interface reaches the class implementing it and `owner.getLastName()` the base class's; a value of a library's type (`List`, `String`) calls none of the project's methods of the name, but for the project's extension methods of it (C#'s `this` parameter's, Kotlin's `fun String.shout()`, Dart's `extension … on`); a bare call in a method may be one it inherits (`getName()` in a subclass); a bare Ruby name standing as a statement that the method has not bound (`setup`) is a call, and a Ruby file sees what the files it requires require, a Dart library what the libraries it imports export. A Rails app's `app/`, `lib/`, `test/` and `spec/` files see one another's classes with no `require`, as its autoloader loads them, and a spec sees what RSpec loads before it — `spec/spec_helper.rb` and `rails_helper.rb`, what they require, and `spec/support/`'s files — so a helper they include (`mock_app`) is called from it. An Elixir bare call reaches its own module's functions, the modules the file `import`s (`import Shop.{Cart, Order}` too), and what each module it `use`s injects — that module's own functions, the modules its `__using__` imports, and in turn what the modules it uses inject — so a test's `insert(:user)` reaches the factory its case template imports and never another module's `insert`, and a library's function (Ecto's `from`, ExUnit's `assert`) reaches none; `user.name` with no parentheses reads a field, and a module the project does not declare (`:crypto`, `Map`) is a library's. A Dart constructor with no body (`CounterCubit() : super(0);`, `const BlocProvider({…});`) is a definition, called where its class is; a named one (`factory Temperature.fromJson(…)`) only by its name, and a mixin's method (`mixin HydratedMixin on BlocBase`) overrides its base's in a class that mixes it in. A project class, in Java, Kotlin, C# and Dart, whose method of a name neither it nor a project class above it (nor, for a value declared as it, below it) defines has it from a library — `hashCode` on a map that extends `AbstractMap` is the JDK's — but for the project's extensions of it. A Play template (`app/views/users/list.scala.html`, Twirl's) is the function it compiles to, `views.html.users.list`, called from a Scala controller as `views.html.users.list(…)` and from a Java one as `views.html.users.list.render(…)`; Play's reverse router (`routes.HomeController.index`) is generated code, no call of the action. Projects that only share a folder — a repository of samples, each with its own build file and none importing another's code — call none of each other's functions, whatever their classes are named; a project that imports a file of another by its path or package name (a Dart example of the package beside it) is one with it, while a Java, Kotlin, Scala or C# import, which names a package any sample may declare, joins none (builds meant as one share a build file above them). `super.save()` (Java, Kotlin, Scala, Dart) and C#'s `base.OnInitialized()` call the base class's method, never the caller's own override — a library's where no project class above it has one. A value a factory returns has the type its function declares (`Users.selectAll()` is a `Query`), else — a guess, which never makes a method the library's — the type it is called on (`Cart.create()`, Scala's `IO.pure(…)` and `IO.unit`); a Kotlin class's name calls its companion object's members, those it inherits too (`User.new { … }` with `companion object : IntEntityClass<User>(Users)`); and a Scala method called with no parentheses (`cart.total`) is a call; a Scala package's member is called through the package — `os.read(p)` runs `object read`'s `apply`, `os.pwd` the package object's `pwd`, and never another class's `read` — and an object called as a function (`RelPath("a")`) runs its `apply`; a type class summoned (`Spawn[IO].background(fa)`, `implicitly[PathConvertible[T]]`, Scala 3's `summon[…]`) is that type class's instance, its methods its own and its bases', or an instance's override. Each call reaches only what its language lets it: a method called on a value of no known type in Java, Kotlin, Scala or C# is some class's method, never a top-level function (but an extension method); a bare call in Dart, JavaScript, TypeScript, Python or PHP is a function's, a constructor's, or a method of the caller's own class or its bases — another class's needs its object; `toString`, `equals`, `hashCode`, `ToString`, `GetHashCode` and their kind on a value of no known type, and Ruby's core methods (`each`, `map`, `where`, `save`) on one, are the library's, as are a Dart test's `expect`, `group` and matchers (`throwsA`, `isA`); the project's code never calls into its tests (a test's helper is called only from tests); and a test class's methods (`StatusCodesTest.get`) are its runner's, so `client.get(…)` elsewhere calls none of them. A value of a type known exactly that the project does not declare has the library's methods, but for the project's extensions: `new AtomicReference(…)`'s `get`, a C++ field declared `std::vector<…>` (a C++ declaration's type is read in lower case too — `logger &l`, `const sink *s` — and `spdlog::pattern_formatter f("%+");` is that class's value, as is what `std::make_shared<logger>(…)` and `std::make_unique<T>(…)` make), a Zig parameter of `*std.Io.Writer` or a value `std` made. A parameter called — `emit(state)` in a bloc handler `(event, emit) { … }`, a callback `cb()` in Dart, JavaScript, TypeScript, Python, Kotlin, Scala, Go, C, C++, C# or Zig — is the value passed, no function of the project's that shares its name. An Erlang or Elixir function is its name and its arity: `parse(A, B)` reaches `parse/2`, never `parse/5`, and so does `x |> parse(y)`, `&parse/2` or `fun parse/2`; an Elixir default lets a call leave its argument out (`def price(item, qty \\ 1)` takes one or two), and a call that no function of its name and arity in the file takes is looked for in what the file imports. A Go call qualified by a package the file imports is that package's: a library package's (`require.Error(t, err)`, `errors.New(…)`) reaches no project function, nor does a method on a value one made (`w := httptest.NewRecorder()`, `w.Header()`), and a project package's (`binding.Validate(v)`) only its own functions. A Go parameter of another package's type (`w *httptest.ResponseRecorder`) calls that package's methods, and a chain of fields from a value of a known type is of its last field's type: `c.Request.Header.Set(…)` with `Request *http.Request` is `net/http`'s, never the project's `Context.Set`, and `c.engine.router.Handle(…)` is `Router`'s. A Go package's variables, declared in one of its files, are of their value's type in all of them: with `var Form Binding = formBinding{}`, `Form.Bind(…)`, `b := Form; b.Name()` and another package's `binding.Form.Name()` reach `formBinding`'s. A Zig function is its container's — the struct its declaration names (`pub const Params = struct { … }`), a generic's function, or a file's own name for itself (`const Analyser = @This();`) — and a value a struct's `init` makes is that struct's (`var p = try Params.init(a)`), so `p.get(…)` reaches `Params.get`, not every `get`; a Zig method's `self` is of the type its annotation names (`self: *NonBlocking`, and `self: *Self` its own container's), and a file's name for a standard-library type (`const Ast = std.zig.Ast;`) makes a value of it the library's, a chain of fields is of its last field's type (`res.headers.get(…)` with `headers: std.StringHashMap(…)` is the library's, `t.arena.allocator()` with `t.zig`'s `var arena = std.heap.ArenaAllocator.init(…)` too, `srv.pool.acquire()` with `pool: Pool` is `Pool`'s), a function's result of a standard-library type the file names by an alias (`const Io = std.Io;`, `fn testStream() Io.net.Stream`) is the library's, while a file imported by name is that file's: `posix.read(…)` with `const posix = @import("posix.zig");` reaches `posix.zig`'s own `read`, and `BufferPool.init(…)` with `const BufferPool = @import("buffer.zig").Pool;` reaches `Pool`'s. A type alias is the type it names: a value declared as C++'s `using daily_file_sink_st = daily_file_sink<null_mutex>;` (or its `typedef`), Kotlin's `typealias`, Scala's `type` or Go's `type X = Y` calls that type's methods. A C++ call through `.` or `->` reaches a class's method over a free function of the same name (`logger->info(…)` is never `spdlog::info`), and a call that names its scope reaches that scope's: `spdlog::info(…)` the namespace's function, never a class's `info`, `fmt::rgb(255, 0, 0)` the constructor of the class it names, and `Base::draw()` the class's or its base's; a C++ class declared with its export macro (`class SPDLOG_API logger { … }`) is the class its name says, its members its own, and a function declared after its specifier macros (`SPDLOG_INLINE std::shared_ptr<logger> get(…)`, `FMT_CONSTEXPR20 FMT_INLINE auto size()`) the function its name says; a bare call in a C++ member function is its class's member first, as C++ looks names up (`listeners()` in `UnitTestImpl` is `this->listeners()`, never another class's). A statement in a C or C++ function body that reads like a declaration (`std::string s(path);`, Qt's `emit finished();`) is no function of the project's, nor is a conversion operator a macro hides from the grammar (`FMT_CONSTEXPR operator string_view()`), and a destructor a C++ header read as C declares is `~basic_memory_buffer`, never what a call of its class runs. A call reaches the overloads that take as many arguments as it passes, in Java, Kotlin, Scala, C#, Dart, Go, Zig, C and C++: a default may be left out (`b: Int = 0`, Dart's named and optional parameters), a variadic takes any number more (`String...`, `vararg`, `params`, `...T`), a Kotlin trailing lambda is one, and a C# extension's `this` and a Zig function's first parameter are passed by the dot of a method call. Of the overloads that take that many, in Java, Kotlin, Scala, C# and C++, a call reaches those its arguments can be passed to, where they say: a string literal reaches `put(String)`, not `put(int)`; `1` not `put(String)`, and in Kotlin not `put(Double)`; `null` no primitive's (in Kotlin, only a nullable type's); a value declared or built as a project class (`Cart cart`, `new Order()`, C#'s `int count`) only an overload of that class or one it extends, and in Java and Kotlin no literal reaches a project class's overload — while C++'s conversions (a string literal to `bool`) and Scala's and C#'s user-defined ones are allowed for. Of those an argument of a known class fits, the most specific is reached: its own class (`sleep(time)` with `time: FiniteDuration` is `sleep(FiniteDuration)`, not `sleep(Duration)`), then a class it extends or implements, or a type parameter of the declaration's own (`template <typename Container>`, `<T>`, `[A]`, which `to_hex(buf)` with a vector reaches before `to_hex(std::span<…>)`), before `Object`, `object` or `Any` (`Send(ping)` with `Ping : IRequest<Pong>` is `Send(IRequest<T>)`, not `Send(object)`), and a C++ function takes as few arguments as its own list allows, or a separate declaration of it does (a header's prototype holding its defaults) — `to_hex(buf)` is never `to_hex(first, last, n = 32)`. Where the arguments say nothing (a call's result, a value of no known type), or no overload fits what they say, the call reaches every overload of the count. A value assigned from a call is of the type the function declares it returns, where every definition of the name agrees; a method's result on a value of a known type, of the type that type's method (or the one it inherits) declares, though other methods of the name return others (`val cell = cells.get(k)` with `cells: Cells` is a `Cell`, whatever `Refs.get` returns), a function declared inside another (a Scala or Kotlin local `def`/`fun`, an anonymous class's method) is no method a call on some other value reaches, while a bare call of it, after it, in the function that declares it reaches it alone; and so is one link of a chain (`repo.find(id).total()` is the found `Cart`'s `total`, `const Pipeline().addMiddleware(m).addHandler(h)` `Pipeline`'s `addHandler`, never an extension of the name on another type): `val adapter = moshi.adapter<T>()` then `adapter.fromJson(…)` reaches `JsonAdapter`'s, `auto l = make_logger()` returning `std::shared_ptr<logger>` reaches `logger`'s, Go's `c, err := NewCart()` the `*Cart`'s; a C# or Java call with no `new` (`var c = MakeCart()`) is a method's result, never a constructor; .NET's service provider hands out the type it is asked for (`sp.GetRequiredService<ApplicationDbContextInitialiser>()`), and a C# name in Pascal case after a value (`scope.ServiceProvider`) is a property, never a type a factory makes. A function passed as a value is used where it is passed: Haskell's `foldr add 0 xs` and `show . add 1`, Erlang's `fun cart:add/2`, Elixir's `&add/2`. C#'s run as `dotnet test` runs them, its test host waiting for netcoredbg to attach (VSTest's host debugging): breakpoints in the tests and in the code they call are hit, and the run ends with VSTest's summary and its exit code. Haskell's run their suite's `main` under GHCi's debugger, in the suite's REPL (`cabal repl test:spec`, `stack ghci`), asked for the test by hspec's `--match` (Tasty's `--pattern`): a failing test ends the run with its exit code, not a stop at the runner's own exit. A Mill program is debugged the same way, by `runMainLocal`. A launcher written without a `#!` line (Mill's own `./mill`) runs through `sh`, as a shell runs it. A remote project's tests are debugged on its host, set up there as they are here (a C or C++ program built there first, its build's lines in the run), under the debuggers installed there; one its debuggers can't reach there runs without them, and says so.
- **Kotlin, Scala and Elixir**: highlighting; the outline (Kotlin's classes, interfaces, enums and their entries, objects and companions, functions, a class's or file's properties, type aliases; Scala 2's and 3's packages, traits, enums and cases, classes, objects, functions, vals and vars, givens and types; Elixir's modules, functions — a function's clauses one item, the same name at another arity another — macros and `@type`s), each definition with its doc (KDoc, Scaladoc — its `{{{ }}}` code and `[[links]]` as Markdown — and Elixir's `@doc`, a heredoc or a string, past the `@spec` under it);
