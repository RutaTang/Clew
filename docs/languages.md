# Language support

**English** · [简体中文](languages.zh-CN.md)

To analyze code well, Clew tailors its support to each language's characteristics. Its features fully support Rust, Python, TypeScript/JavaScript, Go, Dart, Java, C#, PHP, Ruby, Erlang, Haskell and Zig; C and C++, Lean 4 and SQL get most of them, and other languages get some basic support for now, such as syntax highlighting. More languages are coming.

**Settings → Language servers** shows, for the open project, each language's server and how it stands, and lets you set each language up — every setting shows what is in effect before what you can pick:

- **Python** — the interpreter the language server and debugger use, and who named it (your choice, the project's `.clew/lsp.toml`, an environment found for the project). Pick another from the environments Clew finds (the project's own, Poetry, Pipenv, Hatch, PDM, conda, pyenv, uv, or a `python3` on your `PATH`), or give a path. The server is pyright unless you name another under **Any language**: basedpyright, pylsp, jedi-language-server, ruff, ty and pyrefly each run the way they serve, and get the interpreter and the environment's packages where each reads them.
- **Rust** — the Cargo features rust-analyzer loads the project with (every package's features are listed from its `Cargo.toml`; or all of them, with or without the defaults), and the target it checks for.
- **Go** — the build tags gopls and the debugger build with (the tags the project's `//go:build` lines use are listed), and the `GOOS`/`GOARCH` to read the project for.
- **C and C++** — the `compile_commands.json` clangd uses (the ones CMake, Meson and others leave in the project are listed), and flags for files no compilation database covers (`-DDEBUG -Iinclude -std=c++20`).
- **Lean and Dart** — the toolchain their server runs from: elan's toolchains (the one the project's `lean-toolchain` names first), Flutter SDKs and fvm's versions (the project's first).
- **TypeScript and JavaScript** — the TypeScript the server runs: Clew's own by default, never the project's unless you choose it (it is listed, with its version, as running the project's code), or a global install.
- **Zig** — the `zig` compiler zls works with: zvm's and zigup's versions (the one the project's `build.zig.zon` asks for first), or one you name.
- **Java** — the JDK the Eclipse JDT language server builds the project with: the JDKs on your machine (`JAVA_HOME`, `/usr/lib/jvm`, macOS's, SDKMAN!'s, IntelliJ's, asdf's, mise's and Homebrew's), the one of the Java version the build asks for (`.java-version`, `.sdkmanrc`, a Gradle toolchain, the `pom.xml`) first.
- **PHP** — the PHP version intelephense reads the code as (the lowest one `composer.json` allows first).
- **C#** — the solution csharp-ls opens: the `.sln` and `.slnx` files at the project's root and a folder down.
- **Ruby, Erlang and Haskell** — the Ruby LSP of one of your Rubies (rbenv's, chruby's, asdf's, mise's, RVM's; the project's `.ruby-version` first), and the ELP and Haskell language server (ghcup's, Stack's, Cabal's) to run, or the ones on your `PATH`.
- **Any language** — a server program of your own: another build of Clew's server, another server, or one for a language Clew has none for. A server that builds the project still asks before it does. With **Run beside the language's server** on, the program runs as a second server next to the language's own (ruff beside pyright, say): it is sent the same files, and its warnings show with the first server's — underlined, counted in the status bar and said on hover — while definitions, references and hover docs stay the first server's.

Everything is found by reading files — nothing is run — and, for a remote project, on its host. The choices are kept in Clew's own data for this project on this machine, never written into the project, win over its `lsp.toml`, and reach the editor's language servers, the debugger and Ask's code tools alike.

A language whose server is not installed yet asks before Clew downloads its own copy. When the server's program is already on your `PATH` — rustup's rust-analyzer, a clangd you installed — the question offers it too — asked its version first where it answers it, so that a version manager's shim for a tool that is not installed is not offered (TypeScript's is never offered: Clew's own pins the TypeScript it runs, which a server of your own would take from the project): **Use that one** makes it the language's server, as choosing it here would, and nothing is downloaded. A pyright or basedpyright you installed is simply used, with nothing asked or downloaded and no Node needed, unless the project pins pyright's version.

The code the build then leaves out is dimmed as you read: Rust items behind a `cfg` of a feature the package builds without (or of another platform), Go files whose `//go:build` line or `_windows.go`-style name excludes them, C/C++ `#if`/`#ifdef` groups the preprocessor drops for the platform and the `-D`/`-U` flags, Zig's comptime `if`/`switch` branches on `builtin.os.tag` or `builtin.cpu.arch` the compiler does not analyze for the platform, C#'s `#if` groups of the symbols the file `#define`s, Haskell's CPP `#if` groups on `<os>_HOST_OS` and `<arch>_HOST_ARCH` (in a file that turns CPP on), and Erlang's `-ifdef`/`-if` groups of the macros the file `-define`s. Where it depends on the platform, the platform read for is the one picked in the status bar. Only what is certain is dimmed — a feature another package may turn on, or a macro a header may define, is left alone.

- **SQL**: the outline lists a schema's tables (with their columns), views, functions, triggers and types, each with the `--` comment above it as its doc, and the type graph draws the tables joined by their foreign keys — declared in the table or in an `ALTER TABLE` of the same file, as `pg_dump` writes them — and each view to what it selects from. With no language server, the project's schema answers in the code: a table or a column under the pointer (Alt) or at the caret (Show Info) peeks with what the schema says of it — a table's columns, keys, indexes, policies and triggers; a column's type, default, comment and what it references — and Go to Definition goes to the statement that makes it. Names are read as written (`schema.table`, `alias.column`), in SQL files, Prisma schemas and lines of SQL in other code. Weak Spots lists tables with no primary key, foreign keys no index leads with, row-level security left off where the schema's other tables have it, and migrations that drop data, add a `NOT NULL` column with no default, or hold writes to a table (an index built without `CONCURRENTLY`, a column's type changed).
- **Java, C#, PHP, Ruby, Erlang, Haskell and Zig**: highlighting; the outline, each definition with its doc (Javadoc, C#'s `///` XML docs, PHPDoc, Ruby's `#` comments, EDoc, Haddock, Zig's `///`) and tests marked (JUnit, NUnit/xUnit/MSTest, PHPUnit, Minitest, EUnit, Zig's `test` blocks); the import graph; the call graph; and a language server (Eclipse JDT LS, csharp-ls, intelephense, Ruby LSP, ELP, the Haskell language server, zls). The debugger runs Ruby programs under rdbg (the `debug` gem; the chosen Ruby's own), .NET assemblies under netcoredbg, Zig's under lldb-dap, as native code (a `.zig` file is built for the session through LLVM, `-fllvm`, whose debug information lldb reads; a binary from Zig's own code generator — its Debug default on x86-64 — debugs too, but lldb reads no variables from it, and the debug console says so and how to build one it can), and — through debug adapters of Clew's own — Java programs over JDWP, with nothing but the JDK chosen for the project (a `.java` file is compiled for the session; a build's program is named by its `mainClass` and `classPaths`; breakpoints are set as their classes load; locals, fields, arrays and strings are read; and since JDWP evaluates nothing itself, Clew works out Java expressions over it — names, fields, elements, literals, arithmetic, comparisons and logic, string concatenation, and calls such as `order.total()`, `Math.max(a, b)` or `items.get(0) * 2`, an overload chosen and values boxed or unboxed as Java would, the method run in the stopped thread alone, a breakpoint it meets passed; nothing is called for a hover, and nothing from a pause, where the VM runs no method), PHP programs under Xdebug 3, Erlang programs under OTP's interpreter (a module's `main/1`, or the entry the launch names, its application compiled with `debug_info` for the session) and Haskell programs under GHCi's debugger (the project's source directories from its `.cabal` or `package.yaml`; a launch may name `cabal repl` or `stack repl` instead); breakpoints, stepping, the stack, variables and evaluation work in each, as far as the language's own debugger goes: Erlang and Java pause a running program, and so does PHP under Xdebug 3.4 or later on Linux (through Xdebug's control socket), or under an Xdebug that takes commands while the program runs; GHCi steps out by stepping until the function returns, but cannot pause one. All of this works on a remote host too, where Clew's server serves an adapter that listens on a port of that host (rdbg, Go's delve) over its own connection, and debugs Node.js programs with an adapter of its own over Node's inspector — vscode-js-debug, which Clew runs on your machine, opens a connection per debugged process that no remote channel carries. It has breakpoints with conditions, stepping, a real pause (into the program's own code, not Node's), caught and uncaught exceptions, each scope's variables and V8's own evaluation (nothing with a side effect for a hover), and runs TypeScript as Node 22.6 and later does, its types stripped in place, so every line is where the source has it; it follows the main thread, not workers or child processes. A remote project's `composer.json` and Haskell package descriptions are read on its host, so its imports resolve as a local project's do. Imports resolve the way each language builds: Java's packages under the project's source roots (`src/main/java`), C#'s `using` to the namespace the project's files declare, PHP's classes by `composer.json`'s PSR-4 map and its `require` paths, Ruby's `require_relative` and `require` from `lib/`, Erlang's `-include`/`-include_lib` and `-behaviour`, Haskell's modules under the `.cabal`'s or `package.yaml`'s source directories, and Zig's `@import` of a path; what is not the project's (the JDK, NuGet, Composer packages, gems, OTP, Hackage, `std`) is listed by package.
- **Rust**: rust-analyzer, with the project's Cargo features and target (above), and nested Cargo workspaces loaded too. The outline heads each `impl` block's items with what it implements (`Display for Point`), lists a trait's required methods, and sets every item under what holds it. Hovers show their docs as text and examples as Rust; a diagnostic says its code (`rustc(E0308)`); the context menu adds Expand Macro, Memory Layout (rust-analyzer's size, alignment, padding and each field's place) and Related Tests. A `use` of another crate of the workspace resolves to that crate's module (`use acme_core::store` is acme-core's `store.rs`), and a library or binary at a path its `Cargo.toml` names is a crate root — read on a remote project's host too. Run and Debug need no launch file: Clew builds the file's binary or example with your Cargo (the package's own program for a library's module), Cargo's output streams into the run, and a failed build keeps its tab with rustc's errors. **Run Test** and **Debug Test** (right-click a test, the palette, or ⌘U and ⌘⇧K — Ctrl+U and Ctrl+Shift+K on Linux and Windows) run the one test at the cursor alone; one of the library's tests is found in the library, one of the program's in the program. Under lldb-dap, a `Vec`, a `String` and the like read as Rust's, and a panic stops at your code that panicked.
- **Python**: the interpreter is the project's own when it has one, found without running anything — a virtualenv in the project or activated (in a monorepo with one Python project, its venv a folder down, `backend/.venv`), uv's (where `UV_PROJECT_ENVIRONMENT` puts it too), its Poetry, Pipenv or Hatch environment, the interpreter `.pdm-python` records, the conda environment `environment.yml` names or an activated one, or the Python `.python-version` pins (`3.12` is the newest 3.12 pyenv or uv installed) — and Settings says which. pyright sees the environment's packages even where the project's own pyright configuration names its search paths. The outline lists a class's fields (a dataclass's, a pydantic or Django model's, an enum's members) under it with its methods, a module's type aliases (`type Vector = …`, `TypeAlias`, `NewType`, `TypeVar`) as types, its capitalized names as constants and its other assignments as variables, and a function's `@overload` signatures as one entry, whose docs are the ones written on them when the implementation has none; the Docs view takes a module's `__all__` as its API, and renders docstring sections — Google style's `Args:`, NumPy's headings over dashes, Sphinx's `:param:` fields — as headings with an entry per name, and reStructuredText as it reads: admonitions (`.. note::`) as quotes, version notes as a line, code blocks and `::` paragraphs as highlighted code, links as links, and roles (`:func:`, `:pep:`) as code or words. Imports resolve under the source roots `pyproject.toml` names (setuptools, Poetry, Hatch, PDM, maturin's `python-source`, pytest's `pythonpath`, Pyright's `extraPaths`, mypy's `mypy_path`) and `src/`, and to a module's `.pyi` stub where it has nothing else (a compiled extension); a standard-library or installed package's name never resolves to a project file of the same name. **Run** and **Debug** use Clew's own debugpy, downloaded once and checksum-verified, so nothing is installed into the project's environment. A module of a namespace package that imports its siblings relatively runs as `python -m`; a script that lists its packages inline (PEP 723, `# /// script`) runs in the environment uv keeps for it, made first once you agree (`uv sync --script`). While a program run on this computer reads input, its run tab has an input line under the output. `.clew/launch.json` reads Python's configurations as VS Code writes them: `module`, `env` and `envFile`, debugpy's own fields (`justMyCode`, `django`, `subProcess`, …) and variables such as `${workspaceFolder}` and `${env:NAME}`. **Run Test** and **Debug Test** run the pytest test at the cursor by its node id, leaving no `.pytest_cache`, on a remote project's host too — on a line of a parametrized test's case, that case alone (`test_add[1-2]`, named as pytest names it, where it is known from the source); in a test class but in none of its tests, the class's tests; anywhere else in a test file, the file's — and the code menu names what it runs; in a Django project whose pytest is not set up for Django, a test method runs by `manage.py test` and its dotted name. Where the project's Python has no pytest, Clew offers to install it (by pip, or by uv where the environment has no pip; the command is shown before it runs) rather than run the file as a script and call a test that never ran passed. Debug pauses where an uncaught exception is raised, with its frame's variables; Debug Test pauses on the failing assertion, with the test's. A Jupyter notebook reads as its cells, with their saved outputs, or — **Script** in its header — as one `# %%` script in the code view, where its language server reads it as it reads a file: hover, go to definition and references, and its warnings (IPython magics, shell escapes and other languages' cells are left out of what the server reads, and nothing moves); a definition found in the script is shown in the notebook.
- **TypeScript, JavaScript and the web**: `.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.mts` and `.cts` files, HTML, CSS, SCSS and Less, and Vue, Svelte and Astro components, highlighted whole — a component's markup, its script (TypeScript where it says `lang="ts"`) and its styles each in its own language. A component's outline is its script's, each definition with its JSDoc. One TypeScript server reads the project's scripts, with Clew's own TypeScript unless you choose the project's (above); Vue's, Svelte's and Astro's servers read their components, HTML, CSS (SCSS and Less too) and JSON have servers of their own, and a project with a `deno.json` is read by Deno's own server (`deno lsp`, the Deno on your `PATH`), which knows its URL and `npm:` imports and the `Deno` global — its `lsp.toml` can name TypeScript's instead. The servers that load the project's own code — Vue's language plugins, `svelte.config.js`, Astro's integrations — start once the project is trusted. The Node.js they run on is found as you set it up: Volta's, asdf's, mise's or nodenv's, fnm's default, or the newest nvm installed. Imports resolve as the bundler resolves them: relative paths with the extensions and `index` files left out (and TypeScript's `.js` that means `.ts`), the nearest `tsconfig.json`'s or `jsconfig.json`'s `paths` and `baseUrl` (its `extends` and, for a solution config, its `references` followed), a workspace's packages by name (npm, Yarn, pnpm and Bun workspaces) through their `package.json` `exports` — conditions and `*` patterns included, a built `dist/` file read as its `src/` — and `.vue`, `.svelte` and `.astro` imports. Pages and stylesheets are in the import graph too: a page's scripts and stylesheets (`index.html`'s `/src/main.ts`, from the page's folder as Vite reads it), CSS's `@import`, Sass's `@use`, `@forward` and `@import` (partials and `_index` files found, `sass:math` and a package's paths left as the package's) and Less's `@import`. The call graph takes a component rendered in JSX for a call of it, and a global's methods (`JSON.parse`, `console.log`) for none of the project's. **Run Test** and **Debug Test** run the test at the cursor — or the `describe` block, or the file — with the project's own runner: Vitest, Jest, Mocha, Playwright, `bun test`, Node's `node:test` or `deno test`. **Run** runs a file with the project's runtime: Deno where it has a `deno.json`, Bun where it uses Bun, else Node — TypeScript and JSX by the project's `tsx` where it has one, else TypeScript with its types stripped (Node 22.6 and later), which loads an import only by its file's full name (`./util.ts`): a file that imports `./util` or a folder, or that has JSX, is said to need `tsx`, with the command that adds it — and a `package.json`'s scripts are tasks, run by the project's package manager. When the project's dependencies are not installed (its `package.json` declares some and there is no `node_modules`), Run, Run Test and Debug Test offer to install them first with its package manager — the command (`pnpm install`, in the workspace's root) is shown before it runs, and the project's own install scripts run with it — and run once they are in. The project's `package.json`, `tsconfig.json` and `jsconfig.json`, `deno.json`, and its tools' configuration files (ESLint's, Prettier's, Babel's, SWC's, Stylelint's, Turborepo's, Vercel's, Lerna's) are checked and completed against their schemas, which the JSON server fetches from SchemaStore (and Deno's, Turborepo's and Vercel's own sites) the first time such a file is opened. **Debug** runs it the same way, under vscode-js-debug: a Deno project's file under Deno (its inspector, as Deno's own guide sets VS Code up), a Bun project's under Node.js — Bun's inspector speaks WebKit's protocol, which js-debug does not, and the debug console says so. A page is debugged in Chrome or Edge. Debug (or Run) on an HTML page, or on a script one of the project's pages loads, opens that page in the browser installed — Chrome, else Edge — served for the run by Clew on this computer's own address (`http://127.0.0.1:…`, its files and no hidden one, to this computer alone), so its module scripts and root paths (`/js/app.js`) load as they do from a web server; the run's end stops it. A `.clew/launch.json` of `"type": "chrome"` (or `"msedge"`) with the `url` the dev server serves (or a page's `file`) opens it there, its breakpoints in the project's `.ts`, `.tsx`, `.vue` and `.svelte` files reached through the source maps the dev server sends, and the rest of its fields (`webRoot`, `runtimeExecutable`, `userDataDir`, `sourceMapPathOverrides`…) as VS Code reads them; start the dev server first (its script is a task). Where the project has no `.clew/launch.json`, its `.vscode/launch.json` is read (comments and trailing commas too): of its `configurations`, Debug runs the one in the language of the file being read that runs it, else one in its language (a browser's for a page's script), else the first that launches, and names it in the run's output, as it does a `preLaunchTask` it does not run. Debug on a web app's component with no launch file offers that file, at the address its dev server uses (Vite's 5173, Next.js's 3000, Astro's 4321…). A browser runs on this computer, so a remote project's pages are not debugged in one. Weak Spots finds HTML written from strings (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `dangerouslySetInnerHTML`, and a template's `v-html`, `{@html …}` or `set:html`), text run as code (`eval`, `new Function`), shell commands (`child_process`'s `exec`, `shell: true`), a promise's error dropped (`.catch(() => {})`) and checks turned off (`as any`, `@ts-ignore`, `@ts-nocheck`, `eslint-disable`); tests, stories and end-to-end tests are left out. Code statistics leave out lockfiles (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, …) and build output — minified and bundled files, a `dist/` folder's scripts and styles, and files a generator marked — and so do the project graphs (see [Project graphs](project-graphs.md): routes, the component tree, state and workspace packages).
- **Lean 4**: the outline (definitions, theorems, examples, instances — an unnamed one by its class — structures, classes, inductive types) with their `/-- … -/` docs and the file's `/-! … -/` module doc, the import graph, structures that `extends` others in the type graph, and the Lean language server (`lake serve`, from the Lean toolchain elan installs). Lean's syntax is extensible, so a command clew's grammar cannot read is outlined from its first line, and costs no other command its outline. In a Lean file the margin has a **Goals** tab, shown first: it follows the cursor and shows the goals there (the expected type outside a tactic block) and the line's messages, an import that failed wherever the cursor is, and how far Lean has checked the file while it works ("line 40 of 120"; the status bar names the file it is checking) — until Lean reaches the cursor's line, rather than another line's goals. **Step Through Proof** walks a tactic proof one tactic at a time, each step's goals before and after it. **Run** on a file with a `main` runs it as Lean does (`lake env lean --run`, in its Lake project), its output in a run tab; Lean has no debugger, and Run or Debug on a file of proofs says what there is instead. When Lean says a file's imports are out of date, **Restart File** checks it again. A Lake project that uses Mathlib without its build cache — the one the file read is in, a subfolder's included — is offered **Get Mathlib's Build Cache** (`lake exe cache get` in that project, its progress shown) rather than building Mathlib for hours; **Not now** puts the offer away (the palette keeps it). This runs on your machine, not on a remote host. A Lake project in a folder of the one opened has its server run in its own folder (the nearest `lakefile.lean` or `lakefile.toml`); one Lean server runs at a time, and it restarts when you read a file of another Lake project. Lake's `.lake` and `lake-packages` folders stay out of the file tree, search and the index.
