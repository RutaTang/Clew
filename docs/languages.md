# Language support

**English** · [简体中文](languages.zh-CN.md)

To analyze code well, Clew tailors its support to each language's characteristics. Its features fully support Rust, Python, TypeScript/JavaScript, Go, Dart, Java, C#, PHP, Ruby, Erlang, Haskell and Zig; C and C++, Lean 4 and SQL get most of them, and other languages get some basic support for now, such as syntax highlighting. More languages are coming.

**Settings → Language servers** shows, for the open project, each language's server and how it stands, and lets you set each language up — every setting shows what is in effect before what you can pick:

- **Python** — the interpreter the language server and debugger use, and who named it (your choice, the project's `.clew/lsp.toml`, a virtualenv found in the project). Pick another from the environments Clew finds (the project's own, Poetry, Pipenv, conda, pyenv, uv, or a `python3` on your `PATH`), or give a path.
- **Rust** — the Cargo features rust-analyzer loads the project with (every package's features are listed from its `Cargo.toml`; or all of them, with or without the defaults), and the target it checks for.
- **Go** — the build tags gopls and the debugger build with (the tags the project's `//go:build` lines use are listed), and the `GOOS`/`GOARCH` to read the project for.
- **C and C++** — the `compile_commands.json` clangd uses (the ones CMake, Meson and others leave in the project are listed), and flags for files no compilation database covers (`-DDEBUG -Iinclude -std=c++20`).
- **Lean and Dart** — the toolchain their server runs from: elan's toolchains (the one the project's `lean-toolchain` names first), Flutter SDKs and fvm's versions (the project's first).
- **TypeScript and JavaScript** — the TypeScript the server runs: Clew's own by default, never the project's unless you choose it (it is listed, with its version, as running the project's code), or a global install.
- **Zig** — the `zig` compiler zls works with: zvm's and zigup's versions (the one the project's `build.zig.zon` asks for first), or one you name.
- **Java** — the JDK the Eclipse JDT language server builds the project with: the JDKs on your machine (`JAVA_HOME`, `/usr/lib/jvm`, macOS's, SDKMAN!'s, IntelliJ's, asdf's, mise's and Homebrew's), the one of the Java version the build asks for (`.java-version`, `.sdkmanrc`, a Gradle toolchain, the `pom.xml`) first.
- **PHP** — the PHP version intelephense reads the code as (the lowest one `composer.json` allows first).
- **C#** — the solution csharp-ls opens: the `.sln` and `.slnx` files at the project's root and a folder down.
- **Ruby, Erlang and Haskell** — the Ruby LSP of one of your Rubies (rbenv's, chruby's, asdf's, mise's, RVM's; the project's `.ruby-version` first), and the ELP and Haskell language server (ghcup's, Stack's, Cabal's) to run, or the ones on your `PATH`.
- **Any language** — a server program of your own: another build of Clew's server, another server, or one for a language Clew has none for. A server that builds the project still asks before it does.

Everything is found by reading files — nothing is run — and, for a remote project, on its host. The choices are kept in Clew's own data for this project on this machine, never written into the project, win over its `lsp.toml`, and reach the editor's language servers, the debugger and Ask's code tools alike.

A language whose server is not installed yet asks before Clew downloads its own copy. When the server's program is already on your `PATH` — rustup's rust-analyzer, a clangd or pyright you installed — the question offers it too — asked its version first where it answers it, so that a version manager's shim for a tool that is not installed is not offered (TypeScript's is never offered: Clew's own pins the TypeScript it runs, which a server of your own would take from the project): **Use that one** makes it the language's server, as choosing it here would, and nothing is downloaded.

The code the build then leaves out is dimmed as you read: Rust items behind a `cfg` of a feature the package builds without (or of another platform), Go files whose `//go:build` line or `_windows.go`-style name excludes them, C/C++ `#if`/`#ifdef` groups the preprocessor drops for the platform and the `-D`/`-U` flags, Zig's comptime `if`/`switch` branches on `builtin.os.tag` or `builtin.cpu.arch` the compiler does not analyze for the platform, C#'s `#if` groups of the symbols the file `#define`s, Haskell's CPP `#if` groups on `<os>_HOST_OS` and `<arch>_HOST_ARCH` (in a file that turns CPP on), and Erlang's `-ifdef`/`-if` groups of the macros the file `-define`s. Where it depends on the platform, the platform read for is the one picked in the status bar. Only what is certain is dimmed — a feature another package may turn on, or a macro a header may define, is left alone.

- **SQL**: the outline lists a schema's tables (with their columns), views, functions, triggers and types, each with the `--` comment above it as its doc, and the type graph draws the tables joined by their foreign keys — declared in the table or in an `ALTER TABLE` of the same file, as `pg_dump` writes them — and each view to what it selects from.
- **Java, C#, PHP, Ruby, Erlang, Haskell and Zig**: highlighting; the outline, each definition with its doc (Javadoc, C#'s `///` XML docs, PHPDoc, Ruby's `#` comments, EDoc, Haddock, Zig's `///`) and tests marked (JUnit, NUnit/xUnit/MSTest, PHPUnit, Minitest, EUnit, Zig's `test` blocks); the import graph; the call graph; and a language server (Eclipse JDT LS, csharp-ls, intelephense, Ruby LSP, ELP, the Haskell language server, zls). The debugger runs Ruby programs under rdbg (the `debug` gem; the chosen Ruby's own), .NET assemblies under netcoredbg, Zig's under lldb-dap, as native code (a `.zig` file is built for the session through LLVM, `-fllvm`, whose debug information lldb reads; a binary from Zig's own code generator — its Debug default on x86-64 — debugs too, but lldb reads no variables from it, and the debug console says so and how to build one it can), and — through debug adapters of Clew's own — Java programs over JDWP, with nothing but the JDK chosen for the project (a `.java` file is compiled for the session; a build's program is named by its `mainClass` and `classPaths`; breakpoints are set as their classes load; locals, fields, arrays and strings are read; and since JDWP evaluates nothing itself, Clew works out Java expressions over it — names, fields, elements, literals, arithmetic, comparisons and logic, string concatenation, and calls such as `order.total()`, `Math.max(a, b)` or `items.get(0) * 2`, an overload chosen and values boxed or unboxed as Java would, the method run in the stopped thread alone, a breakpoint it meets passed; nothing is called for a hover, and nothing from a pause, where the VM runs no method), PHP programs under Xdebug 3, Erlang programs under OTP's interpreter (a module's `main/1`, or the entry the launch names, its application compiled with `debug_info` for the session) and Haskell programs under GHCi's debugger (the project's source directories from its `.cabal` or `package.yaml`; a launch may name `cabal repl` or `stack repl` instead); breakpoints, stepping, the stack, variables and evaluation work in each, as far as the language's own debugger goes: Erlang and Java pause a running program, and so does PHP under Xdebug 3.4 or later on Linux (through Xdebug's control socket), or under an Xdebug that takes commands while the program runs; GHCi steps out by stepping until the function returns, but cannot pause one. All of this works on a remote host too, where Clew's server serves an adapter that listens on a port of that host (rdbg, Go's delve) over its own connection, and debugs Node.js programs with an adapter of its own over Node's inspector — vscode-js-debug, which Clew runs on your machine, opens a connection per debugged process that no remote channel carries. It has breakpoints with conditions, stepping, a real pause (into the program's own code, not Node's), caught and uncaught exceptions, each scope's variables and V8's own evaluation (nothing with a side effect for a hover), and runs TypeScript as Node 22.6 and later does, its types stripped in place, so every line is where the source has it; it follows the main thread, not workers or child processes. A remote project's `composer.json` and Haskell package descriptions are read on its host, so its imports resolve as a local project's do. Imports resolve the way each language builds: Java's packages under the project's source roots (`src/main/java`), C#'s `using` to the namespace the project's files declare, PHP's classes by `composer.json`'s PSR-4 map and its `require` paths, Ruby's `require_relative` and `require` from `lib/`, Erlang's `-include`/`-include_lib` and `-behaviour`, Haskell's modules under the `.cabal`'s or `package.yaml`'s source directories, and Zig's `@import` of a path; what is not the project's (the JDK, NuGet, Composer packages, gems, OTP, Hackage, `std`) is listed by package.
- **Lean 4**: the outline (definitions, theorems, instances, structures, classes, inductive types) with their `/-- … -/` docs and the file's `/-! … -/` module doc, the import graph, structures that `extends` others in the type graph, and the Lean language server (`lake serve`, from the Lean toolchain elan installs). Lean's syntax is extensible, so a command clew's grammar cannot read is outlined from its first line, and costs no other command its outline.
